## 2. 已核实的现状事实

**A. 已有但不是按「结果」判定的保护**

- 隐藏的轮次常量（**历史**：批次一 `72fc727` 已删除）：`DEFAULT_MAX_TOOL_ROUNDS = 20`、
  面板 `PANEL_ROUND_STRETCHES = 10`、设置上限 `MAX_TOOL_ROUNDS_CAP = 100` → 当时最坏 1000 轮。
  **F4 的处理不是删除，是上移到目标对象并暴露**——现已落为「任务初始预算 + 到点暂停 + 续期」。
- 触顶收尾：`agent.ts:6151` 一次 tools-off 补总结，`:6171` 一行状态文案。
- 重复失败防护：只认 `JS_BLOCKED` / `PERMISSION`（`tool-error.ts:114-119`），阈值 3
  （`:131`），拒绝于 `agent.ts:6350`。**TIMEOUT / STALE_REF 不计入。**
- 执行期判重：**没有**。`recordAction`（`agent.ts:2664-2687`）只写历史不读回；成功调用从不计数
  （开发证实，比 QA 判断更彻底）。
- 上下文回收：`retireOldPageReads` 每轮只替换「上一个」页面读取（`agent.ts:2937-2980`，
  调用点 `:5971`）。**实测净省钱，线性成本，见 §3.2。**
- 上下文压缩：窗口 90% 触发，一轮一次（`context-compact.ts:22-31,53`）；**整段摘要 +
  `hardCapHistory` 原地截断** → 每次压缩放弃一次前缀缓存（开发证据）。
- 对话持久化：正文跨 turn 落盘（`storage.ts:999 saveConversation`），**但唯一的检查点是压缩标记**；
  chat 侧**没有**持久 checkpoint、**没有**成本计数器（工作流运行才有 `checkpoint-store.ts`）。
- 委派：子 Agent 独立循环返回裁剪报告（`orchestrator.ts:121`），每 turn 最多 4 次，**不可恢复**。
- 目标达成判定：**只存在于工作流生成模式**（`prepare_workflow_goal`，`agent.ts:2360+`），对话循环没有。
- 缓存统计：`cachedInputTokens` 从 `prompt_tokens_details.cached_tokens` /
  `cache_read_input_tokens` 解析（`llm.ts:387-394`）；ledger 按**一次 LLM 请求**记账。
- 命中率**没有展示**：`TokensTab.tsx:180-210` 只有 cached 绝对量；`tokenCached` /
  `tokenCacheRate` key 已存在但无消费方（`i18n.ts:2794-2796,4531-4533`）。

**B. 缺口**

1. **成功但无效的重复零计数**：点没反应的按钮、已到底的滚动、空结果的下一页都返回 `ok:true`。
2. **可变失败不计数**：TIMEOUT / STALE_REF 不在 streak 内；目标元素不存在时无限重试。
3. **计数只在单 turn 内有效**：`failureStreaks` 每 turn 新建（`agent.ts:5771`）；Stop 后重发即归零。
4. **面板关掉不中断**：turn 活得比面板长（`agent-channel.ts:4`），全自动模式没有确认卡。
5. **上限对用户不可见**：`i18n.ts:2949` 只说「每批最多操作步数、聊天会自动续期」；结束文案
   `i18n.ts:4313` 不说卡在哪、花了多少。
6. **压缩原地截断**：默认参数下 40 轮**零触发**（256k 窗口 / 阈值 230k / 请求峰值 ~8.7k），
   只在 provider 小窗口或跨很多 turn 时才是问题（QA 快查，见 §3.3）。
7. **落盘的页面读取已被写成「已回收」桩**：`index.ts:3962` 把 `history` 原数组交给
   `saveConversation`，而 `retireOldPageReads` 原地改写 `content`（`agent.ts:2970`）。原文永久丢失，
   下次 `loadConversation` 拿到的是桩 → **R4 续跑只能重读，长任务越跑越贵、越跑越忘**。
   → 最小修复（落盘边界深拷贝）**前移进 R4**，不等 R6a（v5.1）。

### 3.2 retire 的账（v5 口径更正后定稿）

40 轮、每轮 12k 字符页面。**两套口径必须分开写**：

| 口径                         | 总 input           | 未命中     | 命中率  | 每轮未命中中位数 |
| ---------------------------- | ------------------ | ---------- | ------- | ---------------- |
| 开发（活引用，**作废**）     | 241,034            | 9,866      | 96%     | ~250             |
| **QA（冻结副本，定稿）**     | **276,954**        | **48,730** | **82%** | **1,144**        |
| 反事实·不 retire（冻结副本） | 977,940（3.53 倍） | 45,908     | 95%     | 1,070            |

**结论（定稿）**：

1. retire **省的是总输入**（3.53 倍），**不是未命中**——未命中反而比不 retire 多约 6%
   （48,730 vs 45,908）：每少发一段旧内容，断开点之后的尾巴就被多计费一次。**所以「线性回收省 80%」
   这句必须删掉**。
2. 命中率基线不是 96%，是 **82%**；每轮未命中不是 ~250，是 **~1,144**（差 4.6 倍）。
3. 但 retire 仍然净赚（总输入 3.53 倍 ≫ 未命中 +6%），**不能因为未命中上升就删掉它**（见 §6 指标陷阱）。
4. **测量纪律（v5 新增，全项目适用）**：凡是要拿「上一轮请求」做对比的账，必须在**发送时刻深拷贝**
   请求体；引用活数组会被 `retireOldPageReads` 原地改写，事后比对时两边都已变样，差异被抹平，
   **未命中被记成命中，结论系统性偏乐观**。40 轮实测：同一批数据 96% vs 82%，差别只在采样方式。
   复现：`tmp/qa-cache-audit.spec.ts`（冻结口径）/ `tmp/agent-loop-trace.spec.ts`（活引用口径）。

### 3.3 真正的整段重计费点（部分降级为「未验证」）

- **工具表变化：成立**。`load_tools` 后那轮命中率 **96% → 26%**，下一轮回到 98%；冻结口径整体
  71% / 30,955，**QA 独立复现一致**。
- **压缩原地截断：默认参数下没有证据**。QA 快查（`tmp/qa-compaction-probe.spec.ts`，40 轮 × 12k）：
  压缩**一次都没触发**、`hardCapHistory` 也没跑（默认窗口 256k、阈值 0.9 = 230k，请求峰值约 8.7k，
  差一个数量级）；唯一 `[truncated]` 来自页面文本截断（`agent.ts:2653`），不是硬截断。
  → **「压缩是长任务真正的整段重计费点」降级为「小窗口 / 跨多 turn 时才成立」**，须真实 provider
  小窗口实测（provider 报 32k 那种）才有资格当方案依据。
- **压缩收益实测：双窗口为负（定稿，bug 修复后重测）**（QA，2026-11-20，脚本化 provider + 32k 强制窗口）：

  | 窗口   | 压缩                                            | 不压缩                        | 相对       |
  | ------ | ----------------------------------------------- | ----------------------------- | ---------- |
  | 16 轮  | 104,303 input / 31,343 未命中 / 等价成本 38,639 | 105,383 / 28,007 / 35,745     | **+8.1%**  |
  | 100 轮 | 941,115 / 177,339 / **253,717**                 | 1,006,787 / 121,603 / 210,121 | **+20.7%** |

  读法：压缩省总 input **−6.5%**，但每次压缩把前缀整段重计费一次，未命中 **+45%**。
  → **R6b 关闭**，压缩降级为逃生路径（§5 R6b 决策记录）。此前"7 倍 / 5.4 倍"的读数来自
  `c221774` 的 bug 场景（投影丢弃 + 漏回收），**已作废**。
  - **折价口径**：等价成本 = 未命中 + 命中 × 1/10（DeepSeek 官方级缓存折扣）。若主力 provider
    不支持前缀缓存，压缩只会更亏，**结论不变**；换网关不改变"不做 R6b"的判断。
  - **1.2 倍的来源要看清**：`a87b939` 之后 100 轮仍有的 ~1.2 倍余量，**全部来自压缩的重计费**，
    不再是漏回收。→ 若真机上默认参数的长任务也会触发压缩，下一刀是「**何时允许触发压缩**」的策略，
    不是压缩架构（架构已关闭）。
  - **仍是脚本化 provider + 32k 强制窗口**，真机的 input/cached/output 尚未取到（§10 假设 1）；
    AC-7 的数值目标仍要真机数据才算定稿。

## 4. 问题定义

- **F1 真实诉求**：不是「少调工具」，而是「别用无意义的动作假装推进，卡住了就说清楚」。
- **F3 真实诉求**：不是「无界」，而是「**别偷偷把我掐断**」——预算可以有，但必须可见、可改、可续。
- **终止条件（六类，全部显式）**：
  1. **目标达成**（模型声明 + 可校验证据）；
  2. **明确阻塞**（缺权限/登录/信息/页面不支持/不可变更失败）；
  3. **无进展**（连续多轮结果签名不变 → 换策略或终止）；
  4. **用户停止**；
  5. **成本暂停**（累计 token 越过用户阈值 → 暂停并通知）；
  6. **目标预算用尽**（`goal.maxRounds`）→ **不是「已停止」，而是「报告 + 续期/改目标」**。
- **去隐藏上限的代价由三件事兜住，缺一即不可交付**：① 可恢复；② 成本可见 + 秒停；③ 上下文与缓存不被长任务自己毁掉。

### R1（P0）结果型终止（不再有隐藏的次数刹车）

**AC：独占** AC-1、AC-3、AC-9、AC-11；**引用** AC-2（R2）、AC-12（R10）

- 循环里**不存在**未暴露给目标对象或设置的终止常量；终止只走 §4 的六类原因之一。
- 无进展判据基于**结果签名**：同工具同参数连调两次**不算**无进展；判据是「成功返回但页面/任务状态
  没变，且连续多轮」。等待类工具默认不参与计数，除非返回内容同样重复。
- **破坏性操作例外，第二次必须拦**（QA C1，P0 硬红线），不依赖 system prompt 自觉。
- 承载形态参考 dsh：先注入「换策略或收尾」提醒（不 veto），达更高阈值才终止并汇报。
- **落地形态（2026-11-20，`d428770` 进 main，`3d26f99` 补注入哨兵，`1fad8ba` 修不可读判据）**：
  每个页面动作后采样 `progress_signature` → 纯判据 → **提醒 / 拦截**。阈值默认值、可配。
- **计数口径（v13 定稿，文档与实测对齐）**：**第 1 次动作建立基线**，`N` 指**基线之后连续无变化的次数**；
  所以默认「3 次提醒、6 次拦截」的真机表现是——**第 1 次执行、之后连续 3 次无变化时提醒、第 8 次同参数
  调用被拒**（QA 实测：执行 7 次、`nextClicks = 7`、第 8 次被拒）。**口径写「基线后连续 N 次」，不写
  「第 N 次动作」**——否则用户会问"说好 6 次，怎么点了 7 下"。
- **对齐证据（QA，2026-11-20，从 mock 原样抓取模型可见的 note）**：第 5 个请求（此前 4 次点击）收到
  `after 3 successful actions in a row`；第 8 个请求（此前 7 次）收到 `after 6 successful actions in a row`；
  阻塞发生在第 8 次点击（第 9 个请求，间隔 5ms → 拦在 dispatch 前）。两次提醒各只出现一次，不刷屏。
- **关键结论：面板可见文案不带数字**（只有「No progress detected — asking the model to change approach.」
  与拒绝文案），带数字的只有**模型可见的 note**，且给的是「连续无变化次数」——所以用户不会遇到
  「面板说 6 次、实际拦第 8 次」的自相矛盾。**要改的是文档描述，不是代码。**
- **签名不可读的判据（v12 修正，防上线第一天误杀）**：`PDF` / `script-src 'none'` CSP / `chrome://` /
  受限 iframe 上，签名可能一直读不到，而动作本身是成功的（CDP 直点不依赖注入）——若一律按"不可读连击"
  判阻塞，会把任务误杀，用户只会看到莫名其妙的停止。规则：
  1. **签名不可读只在「URL 也没变」时才计入连击**；**URL 变了就算进展并清零**。
  2. 阈值默认 **6**（可配），第 3 次先提醒、第 6 次才阻塞——3 太短，这些页面上读不到签名是常态。
  3. 阻塞文案**必须带当前 URL 与「页面状态不可读」**，不许只给一句笼统的停止原因。
- **提醒注入不得冒充用户发言（P0 约束，2026-11-20 裁定）**：提醒目前用 `role:'user'` + `displayContent:''`
  推一轮给模型——**这与刚修掉的"摘要冒充用户"是同一类手法**。要求：该注入在**落盘数据、历史面板、导出、
  compaction 分段**四处**都不得被当成用户发言**；做不到就改成 system 注入，**不许用 user 角色骗模型**。
- **进度判据（2026-11-20 设计评审三条，必须写进实现）**：
  1. **滚动只作观测，不算进展**：`scrollBucket` 之类的「滚动位置」不得进入进度签名——「滚到底但内容没变」
     正是最典型的长任务空转（C3），只要 `scrollY` 变化就让签名变，等于给无限滚动页面开免检通行证。
     **只有内容 digest 变化才算进展。**
  2. **签名不可得必须有兜底**：chrome:// 页、CSP 阻断、跨域 iframe 可能每轮都返回 `null`；
     若把 `null` 一律当「不计入无进展」，配上已取消的次数上限就是**无界循环**。规则：
     **连续 M 次 `ok:true` 但签名不可得 → 升级为「明确阻塞」并汇报**，`M` 可配。
  3. **续期不清零停滞计数**：用户发新指令 = 新任务（计数归零）成立；但**预算续期不是新指令**。
     停滞计数必须挂在**目标对象**上、与预算一起延续（详见 R10），否则「自动续期 K=1」就变成
     「每次续期重置空转计数」→ **永久空转合法化**。
- **边界**：页面不可读（权限/CSP/about:blank）时状态签名不可得 → 按上面第 2 条兜底，不得静默当成无进展
  也不得静默忽略。
- **内核契约**：若新增 `progress_signature` 之类的 op，必须 bump `kernel-version`，且扩展与 Runner
  两侧内核同步（AGENTS.md §5.6 镜像契约），不许只改 `src/inpage/kernel.ts`。
- **达成判定要新建**：对话循环目前没有，`agent.ts:2360+` 只属于工作流生成。

### R7（P1）缓存代价可观测（不是命中率）

**AC：独占** AC-7

- 展示**总 input token**（主）、**未命中 input**（次）、**整段重计次数**；命中率仅作诊断值。
- 复用已有 `tokenCached` / `tokenCacheRate` key；provider 不回报 cached 时显示「—」。
- 理由：命中率基线 82%，单看它没有区分度（§3.4）；而只看未命中会诱导删掉 retire（§6 指标陷阱）。

### R8（P0）成本可见 + 秒停

**AC：独占** AC-8

- 运行中随时可见「已用 token / 当前步骤 / 卡在哪」；数据来自 R4 的成本计数器（持久，重启不丢）。
- Stop 必须真正停止，**面板关闭不得让 Stop 失效**；停止后不再产生 LLM 请求（结束语除外）。
- **成本护栏（软）**：累计 token 越过用户阈值 → 暂停 + 通知，不硬杀、不是轮次上限。默认值必须存在，
  可改可关。这是长任务对钱包的唯一兜底。

### R9（P2，观察项，不进本轮门禁）

- 用户不在场（面板关闭 / 长时间无交互）：不硬停，降频 + 落 checkpoint，越过成本阈值发通知等确认。
- 降频只作用于**观察类动作**（读页面、截图、轮询）；**写操作绝不降频重试**。
- 依据用「无人交互时长 + 累计成本」，**不得用轮次**。
- 前置依赖 R4 的 checkpoint 与成本计数器；本轮不给 AC，进 §10 假设 5。

### R10（P0）任务目标对象（goal）与显式预算

**AC：独占** AC-12、AC-13

- 每个全自动任务必须有一个**目标对象**，至少含：目标与成功条件、状态（进行中/暂停/达成/放弃）、
  **轮次预算 `maxRounds`**、预算可见位置、变更历史。
- **预算必须显式**：系统给默认值（不能逼用户每次填），但必须在目标卡片上可见、可改；用户随时能调。
  循环里的 `20` / `×10` / `1000` 不再作为默认终止依据。
- **到点不是「已停止」，而是「报告 + 续期」**：报告含 ① 目标原文；② 已完成清单（带证据，可核对）；
  ③ 未完成 / 下一步；④ 停止或阻塞原因（六类之一）；⑤ 成本（已用 token / 已跑轮次 / 是否触及预算）；
  ⑥ 下一步动作（续期 / 改目标 / 停止）。
- **续期语义**：续期必须显式（用户点或无人值守下的既定策略），续的是**增量预算**，不是重置；
  续期后从断点继续，不重做已完成步骤、不重灌历史，**也不清零停滞计数**（停滞状态挂在目标对象上，
  与预算同生命周期——否则续期会变成"重置空转计数"，等于永久空转合法化）。续期次数与累计消耗记入成本计数器。
- **自动续期（K）——只属于无人值守 / 计划任务**（2026-11-20 裁定）：
  1. `K` 默认 `1`、可配、**`K = 0` 表示关闭自动续期**；
  2. **前置条件，不是默认值**：上一段预算内**必须检测到进展**才允许自动续期；无进展 → **禁止自动续期**，
     直接进暂停态等人。否则「卡死」会变成「自动再烧一倍」，比隐藏 20 轮更糟；
  3. **有人在场时绝不自动续期**——只要用户在会话里（面板打开 / 本轮有用户消息），续期只能由用户点；
  4. 每次自动续期必须进目标变更历史：谁触发（哪个策略）、第几段预算、**上一段进展的证据摘要**。
- **架构约束：单一数据源**（2026-11-22 定，依据 `3ac222a`）：
  - **字段所有权**：面板拥有 `maxRounds` / `budgetLog` / `autoRenewals`；循环拥有
    `roundsStarted` / `status` / 停滞计数。`startedAt` 是任务身份，不同即不同任务、不继承。
  - **写入必须合并**：任何一侧落盘前，必须先把存储里的最新值合并进来，**禁止用内存旧副本整份写回**。
  - **预算判定以存储为准**（或判定前重读），内存只用于展示。
  - **反例记档（A1 红，`0d63e0c` 之后仍复现）**：面板把 `maxRounds` 改成 5、界面就地显示
    `3/5`，但落盘的 `maxRounds` 仍是 20 → 循环按 20 跑，最后停在 `20/20`。**用户得到的是
    「改成功了」的错误确认，比改不了更糟**——这类"面板说 5、循环跑 20"的分裂是一切预算语义的前提。
- **目标寿命 = 任务寿命，不是会话寿命**（2026-11-20 定，核心原则）。现状 `beginTask` 只在
  「当前没有目标」时建（`agent.ts:5772`），全仓没有把 goal 置 `done`/`abandoned` 的路径 → 同一会话的
  第一个目标会永生。后果四个：① 第二句换任务仍继承旧 `maxRounds`/`roundsStarted`/`autoRenewals`；
  ② 旧目标 `paused` 时新任务一开口就是暂停态、直接看到「预算用尽」卡片；③ 恢复注记与报告里的
  「已完成」是上一个任务的，模型会被误导跳过步骤；④ 点续期续的是旧目标。四条规则：
  - **R-1**：新用户消息时，旧目标为 `paused`/`done`/`abandoned` → 归档旧的（未达标记 `abandoned`）并
    **新建目标**；预算、`autoRenewals`、停滞计数随新目标重置。
  - **R-2**：旧目标 `active` 时的新消息 → **并入当前任务**，不重置预算；要换任务必须走显式入口
    （面板「结束并新建」），**不靠猜语义**。
  - **R-3（v16 重写）**：**完成判定只来自显式声明 + 可校验证据，不许从行为推断**。模型必须调用显式完成入口
    （`goal_complete` 工具或等价命令），提交 `summary` + `evidence[]`，**至少一条证据是 URL / 元素 / 文本**；
    系统只校验「证据存在且可定位」，**不做语义判断**。**没有声明的，目标保持 `active`** 并跨 turn 连续，
    状态行写「任务进行中」。
    - `unfinished` **从目标对象的未完成步骤产出，不从模型散文里猜**。
    - 代价（可能留僵尸目标）由 R-2 并入 + 面板「结束并新建」对冲，**不许用"没失败就当完成"来省事**。
    - **反例记档**：`ef2eb9e` 曾实现为「正常答复且无失败步骤 → done」。这不是保守，是把显式预算架空——
      模型安静地停下、什么都没干成也会被判 `done`，下一条消息立刻「新任务 0/20」，预算与 `autoRenewals`
      每轮清零，且从面板看不出来。**一句话：不许把"没失败"当"完成"。**
  - **R-5（归档）**：目标对象要有**有界归档**（保留最近 **3 个**已结束目标），否则用户问「上个任务做到哪了」
    只能答「没了」，AC-13 的目标变更历史也查不到。
  - **R-4**：预算耗尽 / 用户 Stop → `paused`，**不自动续跑**；续期只走命令。
- **两个显式入口必须同批交付**：面板「**续期**」与「**结束并新建**」（AC-13⑦ 的硬规则）。
- **资源说明须显式**：目标对象上还要写明 fan-out 限制（`每 turn 最多 4 次委派`，默认 4、可配置）
  与成本阈值，理由同预算——限制可以存在，但不许藏着（AC-12）。
- **放弃/改目标**：改目标视为新任务，旧预算与进度归档，不复用。
- **边界**：任务一开始就无法建目标对象（如用户只发一句话闲聊）→ 不建，按普通对话处理，不得报错。

**交互说明（「可见性」的落地，R10 的验收依据）**

| 场景          | 行为                                                                                                                              | 边界 / 异常                                      |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 任务开始      | 对话区顶部出现**目标条**（粘性一行：目标摘要 + 预算进度 `8/20` + 状态）；不遮挡消息                                               | 闲聊不建目标条，不占位                           |
| 查看完整目标  | 点目标条展开：成功条件、`maxRounds`（可直接改）、已用 token、已执行破坏性操作数                                                   | 改预算立即生效，记入变更历史                     |

**用户路径变化（必须写进 i18n 与发布说明）**：以前到顶自动收尾（`agent.ts:6151`），现在到顶进入
「暂停待决策」——**没有被用户或既定策略确认，就不会自动继续，也不会静默结束**。

**对已有功能的影响**：① 手动确认模式不引入目标条（普通 chat 不受影响）；② 计划任务 / 无人值守走
默认策略；③ 工作流运行不套用目标对象（它有 runner 自己的预算），避免两套预算打架。

**自动续期（K）已裁定（2026-11-20）**：无人值守时没人点「续期」，所以目标对象必须带自动续期上限 `K`
（默认 1、可配、`0` = 关闭）。**但 `K` 不是「再给一倍预算」的默认语义**：自动续期的前提是
「上一段预算内检测到进展」，无进展一律禁止自动续期；有人在场时也绝不自动续期；每次自动续期都必须
留痕（触发者、第几段、上一段进展证据）。细则见 R10。

## 6. 指标口径（全部复用现有 token-ledger）

**口径裁定（2026-11-20，已收敛，定稿）**：

- **验收一律用「实际发出」口径**：以每次请求实际发送的字节 / token 为准，provider 计费看的就是实际
  发出的内容；数据源是 `token-ledger` 的按请求记录（`inputTokens` / `cachedInputTokens`）。
- **「冻结副本」是测量方法，不是第二个口径**：在 `streamCompletion` 被调用的那一刻把整个请求
  深拷贝一份；拿它算「上一轮请求」的真实成本。**反事实**（"不做 retire 会花多少"）只能用这种方式，
  且必须标注「模型推算 + 冻结副本」。
- **测量纪律（全项目适用）**：凡是要拿「上一轮请求」做对比的账，必须**发送时刻深拷贝**。引用活数组
  会被 `retireOldPageReads` 追溯改写，差异被抹平，**未命中被记成命中，结论系统性偏乐观**（实测
  96% vs 82%，见 §3.2）。
- **§3 的缓存基线以 QA 冻结口径为准**：命中率 **82%**、每轮未命中 **~1,144**、40 轮未命中 **48,730**。

**指标陷阱（必须写进任何报表，否则会诱导错误决策）**：

- **主指标 = 总 input token**（这是钱）；**次指标 = 未命中占比 / 每轮未命中**（这是缓存效率）。**两个同看。
- **禁止单凭未命中上升判定一个优化是坏的**：retire 让未命中 +6%，但总输入省 3.53 倍——只看未命中会
  诱导把 retire 删掉，那是净亏。反过来，**也禁止单凭总输入下降就放过未命中暴涨**（说明在拿全量重发
  换便宜计价）。
- **实战例证（2026-11-20）**：压缩省总 input **6.5%**、未命中涨 **45%**，等价成本 **+20.7%**。
  只看"总 input 下降"会得出"压缩很划算"的相反结论——这是双指标同看第一次抓到真实误判。

**通用验收条款（v5 起，v20 共 11 条）**：

1. **不触发的 AC 不算通过**：任何 AC 必须证明「目标代码路径真的被执行过」（触发计数 ≥1 / 事件存在 /
   日志可查）。只跑绿、路径没进，一律记为**未验证**，不得写成通过——虚假全绿比挂测试更危险。
2. **不写的数不许当依据**：没有测量方法（口径 + 采样方式）的数字，不得进 AC、不得进对外结论。
3. **口径变更必须留痕**：任何改变基线数字的调整，写进 §3.4 并标注撤回原因，不许悄悄改数。
4. **一个 AC 只有一个 owner**：AC 不得跨任务挂靠（一个阀门握在后面才做的任务手里 = 实际上没人负责）。
   跨 R 只能「引用」，不能「挂靠」；R4 交付时 AC-5⑤ 必须真绿，不等 R6a。
5. **花 token 必须有生效断言**：任何花 token 的路径（压缩摘要、补总结、重写、二次评审）必须断言
   「算出来的效果真的被应用了」——`调用次数 ≥1` 且 `被应用的请求数 ≥1`，两者不匹配即失败。
   这次是 1 次摘要调用真花了钱、8 个请求一个都没带上它：**比不触发更糟，因为它看起来做了**。
6. **回归用例必须先在 bug 版本上红、修复版上绿**（红→绿两次输出贴在用例里）。**在 bug 版本上会全绿的
   测试等于没有测试**——这是 2026-11-20 组合矩阵被判"硬伤"的原话。同时：手工复刻拼装顺序不算
   覆盖，**bug 在循环里的必须走真循环**。
7. **用户会数数的阈值必须写清计数口径**（2026-11-20 教训）：凡是在 UI 上承诺次数/轮数的地方，
   必须写明"从哪里开始数、数的是什么"——**统一写成「基线之后连续 N 次（无变化）」，禁止写成「第 N 次动作」**。
   文档写的次数与真机表现对不上，用户就会觉得我们在乱报数；**优先把用户可见文案做成不带数字的**，
   数字只留给模型可见的 note。
8. **有界日志不得当配额账本**（2026-11-20 教训）：展示用日志必然被截断（`slice(-MAX_BUDGET_LOG)`），
   用它数配额会让安全网在阈值>上限时**静默失效**（实测 `K=25` 时 25 次自动续期后仍 `allowed`）。
   配额一律用**单调递增计数器**（如 `autoRenewals`），日志只负责留痕。
9. **「暂停等人类决策」必须与入口同批交付**（2026-11-20 硬规则）：任何会让任务进入"等待用户决策"状态的
   改动，必须同一批交付用户入口（目标条 / 卡片 / 续期命令），否则**不许合入**——没有入口的暂停
   = 永久挂起，比原来的上限更差。
10. **已验的路径被改，绿就作废**（2026-11-22 定）：任何改动触及某条 AC 走过的代码路径，该 AC 的绿
    必须重验才算数；改动落在**公共写入/读取路径**（如 progress 合并、续期、归档）时，重验范围要扩到
    所有走这条路径的 AC，不能只验主角那条。**验收通过的是"某次提交的行为"，不是"这个功能"**。
11. **红证据拿不到时怎么办**（2026-11-20 裁定）：允许用不改生产常量的夹具（如 `run_javascript` 返回大结果）
    补 loop 级红，但**以"一小步改动"为上限**，不许为凑红把 CI 拖成分钟级、更不许改生产上限；
    仍做不到的，如实写成「**loop 级红不可得，回归由单测级红 + loop 级不变量覆盖**」，并把限制写进测试文件
    注释。**不许假装红了。**
