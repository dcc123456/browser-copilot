# 结果型无进展判定 · 设计草案（R1）

> 状态：草案，待产品经理合入
> `specs/2026-11-20-agent-loop-and-token-cache-design.md`（R1 / AC-3）。
> 本文只回答三个问题：结果签名是什么、等待类白名单怎么划、无进展与破坏性重放的优先级。
> 不含代码，先对齐再实现。

## 1. 结果签名（ProgressSignature）

### 1.1 组成

一次工具调用之后，取一个**页面结果签名**，与调用前的签名比较：

```
signature = hash(
  url                      // origin + path + 排序后的 query
  readyState
  interactiveDigest        // 可见交互元素按文档顺序的 [role, name, value(截断), disabled, checked]
  textDigest               // 可见文本长度 + 前 50k 字符的滚动哈希
)
```

- **滚动位置不进签名**：滚动只有"露出新内容"才算进展，而新内容会改变 `textDigest`；把 `scrollY` 放进签名等于给"滚到底但内容不变"的无进展页开免检通行证（C3 正是这种页面）。
- 不复用现有 `page_signature`（kernel.ts:2150 的 `href|readyState|元素数|文本长度`）作为判据：它把"文本长度不变"当同意，价格从 10 改成 20、勾选状态变化都看不出来。它可以继续做 settle 探针，但**不能做进展判据**。
- 新增一个 kernel op `progress_signature`：只读、同步、有界（交互元素取前 200 个，文本哈希滚动读取前 50k 字符），单次成本目标 < 5ms，不进模型上下文。
- 任务清单版本并入签名：`completedSteps` 数量或最后完成步骤 id 变化 = 进展（工具没改页面但完成了待办，也算进展）。

### 1.2 抗噪

- **只在 settle 之后取签名**：复用 `waitForPageStable`（网络 idle 优先，DOM 签名轮询兜底，agent.ts:5233），避免动画/异步渲染把同一状态算成两次进展。
- **不稳定区域剔除**：`textDigest` 只取 `body` 可见文本，跳过 `script/style/noscript/template`；不做 OCR、不读 iframe（跨域拿不到，硬读会把"不可读"误判成"没变化"）。
- **已知抖动**：计时器、轮播、广告 iframe 会让签名每轮都变。判据不是"完全相等"，而是「**连续 N 次观测到的签名都在同一个等价类里**」——等价类由实现里的 normalization 决定（时间/计数类文本不剔除，先接受误报为"有进展"，宁可漏判也不误杀）。
- **签名不可得时不得判无进展**：`about:blank`、`chrome://`、CSP 阻断、权限拒绝、driver 超时 → 返回 `null`，走"明确阻塞"路径，绝不把 `null == null` 当成没变化。
- **`null` 连击必须升级**：连续 `M` 次（默认 3，可配）工具 `ok:true` 但签名均为 `null` → 升级为「明确阻塞」并汇报（缺权限/页面不可读/需要换目标）。没有这一条，取消轮次上限后 `null` 就是无界循环的唯一入口。
- **观测工具本身不产生进展**：`snapshot_page` / `read_current_page` / `screenshot` 只读取签名，不刷新"进展事件"时间戳；否则模型反复读页面就永不判无进展。

### 1.3 什么算"一轮无进展"

同一 turn 内，一次工具调用被判定为无进展，当且仅当：

1. 调用**成功**（`ok:true`），且
2. 调用前后 `signature` 相等（或等价类相同），且
3. 任务清单版本未变，且
4. 该调用不在等待类白名单里（§2）。

连续 `N` 次（默认 3，可配置）无进展 → 进入"停滞"状态：

- 第一次到达：注入一条系统提醒（"同一结果已重复 N 次，换策略或汇报卡点"），**不拦截**，因为合法轮询/等待可能仍会成功；
- 第二次到达（再 N 次）：只拦截**同一 (tool, args)** 的再次调用，要求换参数/换工具/汇报；**不拦截其他任何动作**——换策略本身就是要求的响应。
- 破坏性动作的重复不进入这套计数，见 §3。

## 2. 等待类白名单

| 类别           | 例子                                               | 是否计入无进展             | 理由                                                       |
| -------------- | -------------------------------------------------- | -------------------------- | ---------------------------------------------------------- |
| 显式等待       | `wait_for`、sleep、轮询接口                        | **不计入**（默认）         | 等待本身不改变页面，是任务的一部分                         |
| 观察           | `snapshot_page`、`read_current_page`、`screenshot` | 不计入                     | 读状态不产生状态                                           |
| 瞬时失败       | STALE_REF / TIMEOUT / ELEMENT_NOT_FOUND            | 不计入进展，也不计入无进展 | 下一次快照可能修好；但同一失败重复由既有 failure-streak 管 |
| 用户输入       | `ask_user`、`present_plan`                         | 不计入                     | 不是页面动作                                               |
| 写入/点击/导航 | `click`、`fill`、`open_url` 等                     | 计入                       | 这才是"动作成功但页面没变"的主体                           |

补充规则：

- **等待类"结果重复"仍要计数**：`wait_for` 连续超时且返回文本完全相同，不计入无进展，但计入**独立的等待停滞计数**（阈值加倍，默认 6），到达后提醒换策略。理由：目标元素不存在时，`wait_for` 就是无限重试。
- **等待宽限**：同一签名持续期间，若距上次状态变化 < 10s，不判定无进展（异步任务正在跑）。超过 10s 仍不变，才开始计入。
- 白名单是**工具名级**的，不做参数猜测；新增工具默认计入（保守），由实现显式加白。

## 3. 与破坏性重放的优先级

固定顺序，不允许互相吞掉：

1. **工具禁用 / 模式拒绝**（既有）
2. **不可逆动作重放栅栏**（R2，`repeatedIrreversibleOp`）：同一 (tool, args) 已执行过 → **dispatch 前拒绝**，与页面是否变化无关。
3. **无进展拦截**：只拦同一 (tool, args) 的重复，不拦不同动作。
4. **不可变失败 streak**（既有 JS_BLOCKED / PERMISSION）

理由：一个"提交"按钮点完页面确实变了（成功页），无进展判据会认为"有进展"，但第二次提交仍然是灾难。所以重放栅栏必须在最前，且**不受签名影响**。反过来，无进展拦截绝不能顺手拦掉"换一个按钮再试"——那正是我们要模型做的事。

## 4. 观测与验收对应

- 每次无进展判定产出一条事件：`{ turn, step, tool, argsFingerprint, signatureBefore, signatureAfter, waitedMs }`，供 M2（无进展轮次占比）与 R3 终止事件使用；不新增 token 统计。
- AC-3 的"识别后必须有动作"：停滞状态下，模型下一次调用若不是"同指纹"即视为已换策略，清零计数；若仍是同指纹 → 拦截 + 三要素反馈（URL / 为什么 / 要用户做什么）。
- 测试：纯逻辑单测（等价类、白名单、null 签名、阈值）；集成用 QA 的 `/noop` 页面（下一页成功但 DOM 不变）验证 N 次后拦截；用动画页验证不误杀；用 404 元素验证等待停滞计数。

## 5. 续期与停滞计数

- **新用户指令 = 新任务**：停滞计数随新目标清零。
- **续期不是新指令**：`maxRounds` 续期只增加预算，**不得清零停滞计数**，否则「自动续期 K」会把空转合法化成无界任务。停滞状态与预算同生命周期，挂在目标对象上（R10），不另开一份状态。
- 目标被修改（不是续期）时按新任务处理，旧进度归档。

## 6. 实现约束

- 新增 `progress_signature` 注入 op 必须 bump `kernel-version`，并同时更新扩展侧与服务 Runner 侧使用的同一个计数/版本号；两侧内核镜像必须同步（AGENTS.md §5.6），不能只改 `src/inpage/kernel.ts`。
- 判定逻辑必须纯函数可测：签名等价类、等待白名单、`null` 连击、续期不清零，全部单测覆盖。

## 7. 明确不做

- 不做语义级"这一步有没有推进目标"的判断（模型自评不可靠，成本高）。
- 不做跨 turn 的无进展累计：新用户指令 = 新任务；破坏性清单除外（R4⑤，已持久化）。
- 不做逐像素截图比对：成本高、抖动大、隐私面大。
