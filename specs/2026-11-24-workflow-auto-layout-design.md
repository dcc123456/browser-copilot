## 2. 现状事实（代码级）

- `auto-layout.ts` 分层：Kahn 拓扑排完后，**剩下的环内节点按 `ids` 数组顺序直接追加**（约 149→165 行）；
  分层时对**所有**前驱取 `max(layer+1)`（约 171 行），**包括回退边**。
  → 同一张图只把节点数组反序，`n2` 从第 2 层掉到最后一列、5/7 条边向左。**数组顺序会随导入 / 生成 /
  重新保存而变**，所以用户会遇到"昨天排好的图今天排不一样"。
- 跨行折行是 Z 形：下一行从上一行起点开始，导致正向边**向左回折**。这条**与回退边无关**
  （不收回退边的对照组同样 2/6 条向左）。
- 编辑器本身能从 **`sourceHandle` 认出回退/fallback 边**——不必靠 DFS 去猜。

## 3. 产品判断

- **确定性是正确性**，不是风格：同一个输入两种输出，用户会以为图坏了、或者自己接错了线。
- ~~**正向边一律向右**~~ → **已否决（2026-11-24，用户反馈 + admin 撤回）**：阶梯式折行导致整张图
  沿斜线向下生长，用户看不到整体流程。**不能接受画布更宽的抽象结论**——要看真实编辑器截图。
- **正确方向（admin 定）**：**同一层纵向堆叠、分层按横向展开**。主线是一条横轴，条件分支展开成
  并排的支路，回退线仍只作回退、不参与分层。
- **零交叉不是目标**：追求最小交叉是 NP 难，把不可达标准写成 AC 只会逼出假绿。交叉数**只记录**。

## 4. 需求

### R1（P0）回退边必须被识别并从分层中剔除

- **按图结构判定（拓扑优先）**，不靠 `sourceHandle`：2026-11-24 实测，用户手画的回退线和普通正向边
  **用的是同一个 handle**（`javascript-code-output-1`），`-output-fallback` 只是**错误回退端口**
  （`onError → fallback`，另一种语义），分不出"把线接回前面的算子"。所以 handle 只能覆盖错误端口那一类。
- **判定方式**：强连通分量里以"有外部入边的节点"为入口排深度，只抽**真正指回上游**的边；
  `onError` fallback 端口作为**第二重**直接排除。手画回退线（无区分 handle）照样能被排除。
- 实现记录：`8df8b97`（拓扑判回退边 + 阶梯折行 + 确定性），旧代码上 3 条用例先红后绿。
- 剔除后按剩余正向边分层；环内节点不得"按数组顺序追加"决定层级。

### R2（P0）排版必须确定

- **同一张图、节点与边集合相同 → 排版结果逐字节相同，与节点数组顺序无关**。
- 排序/并列时的次级比较必须用**稳定键**（如节点 id），不得依赖数组下标或插入顺序。

### R3（P0）分层横向展开、同层纵向堆叠（阶梯斜线已否决）

- **分层按横向展开**：同层级的节点排成一列（纵向堆叠），不同层级按从左到右推进。
- **同一层纵向堆叠**：条件分支的各支路在同一列（或相邻列）纵向排列，不形成长斜线。
- **整体形状接近横向矩形**，不是越走越斜；主线是一条横轴。
- **正向边方向不再作为硬判据**（用户明确不要阶梯斜线）；交叉数只记录。

### R4（P0）不改变图的结构

- 排版只改坐标（与视口），**节点集合、边集合、节点参数一律不变**；不得增删节点、不得改写 `blockId`。

### R5（P1）交叉与宽度只记录

- 交叉边数、画布宽高**作为观察指标记录**，不设阈值；出现明显劣化时在验收记录里注一笔，不判红。

## 5. 验收标准

| 编号 | 对应需求 | 判据                                                                                                | 方法                                                    |
| ---- | -------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| AC-1 | R3       | **长链分支不能形成长斜线**：典型工作流排版后接近横向矩形（宽高比 ≥ 2:1），不是越走越斜              | 单测 + 真机截图                                         |
| AC-2 | R3       | **不重叠**（节点矩形两两不相交）                                                                    | 单测 + 真机                                             |
| AC-3 | R2       | **确定性**：同一张图的节点数组随机打乱 **5 次**，排版结果**坐标逐字节相同**（按节点 id 排序后比较） | 单测（旧代码须红：5 种顺序 → 5 种坐标；`8df8b97` 起绿） |
| AC-4 | R5       | 交叉边数**只记录不判阈值**；报告里给出数值与相对手摆基线的变化                                      | 观察项（不判红）                                        |
| AC-5 | R4       | 节点数 / 边数 / 各节点 `blockId` 与参数**排版前后完全一致**                                         | 单测 + 真机                                             |
| AC-6 | R1       | 带回退分支的图：`cond` 必须排在它后继的**左侧**；节点数组反序后结果不变                             | 单测（旧代码须红）                                      |
| AC-7 | R3       | **排版后适配视口时字号不能小到看不清**：`fitView` 后节点文字可读（真机截图人工判断，不能只看坐标）  | 真机截图（必须）                                        |
| AC-8 | R3       | **同层纵向堆叠**：条件分支的各支路在同一列（或相邻列）纵向排列，不形成长斜线                        | 单测 + 真机截图                                         |

**为什么交叉数不设阈值**：最小交叉是 NP 难，任何"零交叉"的 AC 都不可达；写成硬判据只会让人为了绿
去调参或放宽断言——那是假绿，比不测更糟。**能判的（不重叠、确定性、结构不变、横向矩形）才写成 AC。**

**为什么阶梯斜线被否决**：用户明确反馈"看不到整体流程"。**画布宽一些可以接受**是抽象结论，
真实编辑器里 fitView 后字号小到看不清，等于没解决。AC-7 要求真机截图人工判断可读性，不能只看坐标。

**红→绿要求**：AC-1 / AC-3 / AC-6 / AC-8 必须在旧代码上**先红**（QA 已复现：交叉 1→3、`n2` 掉到最后一列、
`n3→n4` 向左、阶梯斜线），再在修复版上验绿。打不出红的一律记「未受考验」。

## 6. 暂不采纳

| 想法                       | 不做的原因                                               | 未来触发条件                                     |
| -------------------------- | -------------------------------------------------------- | ------------------------------------------------ |
| 零交叉 / 交叉数阈值        | NP 难，不可达标准会逼出假绿                              | 不做                                             |
| 靠 DFS 猜回退边            | 编辑器已能从 `sourceHandle` 认出；猜出来的集合在边界不稳 | 只有在 handle 信息缺失的路径上才退回猜测，并记录 |
| 保留 Z 形折行              | 正向边向左回折，用户会怀疑接错线                         | 不做                                             |
| 自动排版时同时清理孤立节点 | 越权改动图结构                                           | 用户明确要求时                                   |
