## 2. 现状事实（代码级）

- **保存链路**：`App.tsx` 的 `handleSave` → `workflows.save`；worker（`background/index.ts:1902`）
  先 `carryStoredWorkflowFields`、再 `commitWorkflowRevision`、最后 `saveWorkflow`。
- **每次保存都 +1，不看内容**：`commitWorkflowRevision`（`workflow-revision.ts:52`）没有内容比较。
  所以"连续保存两次、没改"现在会产生 **2 条** revision——与需求冲突。
- **已有 20 上限，只是元数据**：`REVISION_HISTORY_LIMIT = 20`（同文件:20）；
  `WorkflowRevisionMetadata` 只有 `revision/updatedAt/source/parentRevision/repairSessionId`
  （`types.ts:285-291`）——**没有图快照**，"应用旧版本"目前做不到。
- **历史存在工作流 JSON 内部**（`types.ts:357`）——历史一进 JSON，每次保存内容都不同，按内容判等永不相等。
- **落盘会剥 data URL，但只作用于副本**：`storage.ts:286` 在 `saveWorkflow` 里
  `const storable = shedBulkDataUrls(canonical)`，**函数入参 `workflow` 不改**。所以快照若拿内存原对象
  算指纹/写键，会带上未被剥离的大块数据（`storage.ts` 注释记过 36MB 单图的实测）。
- **`shedBulkDataUrls` 只认 `data:` URL**，且有 `MIN_BULK_DATA_URL_CHARS` 下限：**不是"体积兜底"**，
  普通超长字符串它不管。
- **体积实测（2026-11-24，QA 与开发各测一次，结论一致）**：

  | 样本                            | 体积                          | 节点 |
  | ------------------------------- | ----------------------------- | ---- |
  | 仓库内真实 / 夹具工作流（7 个） | **0.7–3.9 KB**（中位 1.4 KB） | 2–7  |
  | 合成 100 节点、参数 600 B       | 85 KB（×20 = 1.7 MB）         | 100  |
  | 合成 200 节点、参数 600 B       | 171 KB（×20 = 3.3 MB）        | 200  |

  → 20 个版本对正常图是**几千倍余量**；体积上限是安全网，**不是调参旋钮**。

- **入口**：工具栏 tab 依次 日志 / 目标 / 数据表 /（参数）（`TopToolbar.tsx:136-143`）；版本按钮放数据表之后。
- **撤销**：`App.tsx` 的 `pushHistory` 记录整张画布快照，AI 改动也是整批撤销。

## 3. 产品判断（先把两件事拆开）

- **编号（revision）** 服务并发控制与来源留痕（AI 修复、广场更新靠它判基线）——**本次不动**。
- **快照（version）** 才是用户要的"能回去的版本"——新建独立存储，按内容哈希去重。
- 两者会分叉：**revision 每次保存都涨，版本只在内容变化时涨**。列表里必须同时显示且区分：
  `版本 N · 保存序号 M`，别让用户以为是一个数。

## 4. 需求

### R1（P0）入口与弹窗

- 工具栏「数据表」右侧新增「版本」按钮（图标 + 文案，中英双语），点击开弹窗。
- 列表倒序；每行：`版本 N · 保存序号 M`、时间（`YYYY-MM-DD HH:mm`）、来源、摘要、体积；
  行内操作：**预览 / 应用 / 删除**。
- **空状态**：还没版本时写"保存一次后这里会出现版本"，不显示空表。
- 关闭方式（遮罩 / Esc / 关闭按钮）只关弹窗，**不改画布**。

### R2（P0）什么算"一个版本"

- **只有内容变化才新增**；判等用**规范化 JSON 的 SHA-256**，不是时间戳、不是 revision。
- **参与判等**：节点（类型、参数、id、位置）、边、触发器、名称/描述/设置、变量声明。
- **不参与**：视口（`position`/`zoom`）、`updatedAt`、`revision`、`revisionHistory`、**版本索引本身**。
- **算保存的动作**：编辑器保存、生成落盘、AI 修复落盘、广场更新落盘——**都记**，`source` 沿用既有词表。
- **不算**：参数面板保存（`workflows.parameterValues`）、运行、纯浏览。

### R3（P0）快照必须与落盘**同形**

- **快照取「落盘最终形态」，不是「内存形态」**：走完 `carryStoredWorkflowFields → commitWorkflowRevision →
规范化 / 补默认字段 → shedBulkDataUrls` 之后**真正要写进存储的那个对象**，再算指纹、统计字节、写键。
  "跑一遍 migrate"不叫同形——**规范化补上的默认字段（如 `settings`）必须已经在里面**，否则同一张图会算出
  两个指纹，产生一个只差默认值的"幽灵版本"（2026-11-24 实测：API 建图不带 `settings`，保存后规范化补上，
  再进编辑器保存就多出一版）。
  - 否则：列表里的体积是假的；应用旧版会把本该剥掉的大块数据装回画布；同一张图算出两个哈希、去重静默失效。
- **耦合约束**：将来若 `saveWorkflow` 开始截断（如 `capPersistedStrings`），快照**必须在同一批里跟着截断**，
  不许单边演化。
- **本次明确不做**：快照单独加 8KB 截断。理由：落盘不截断而快照截断，应用旧版会**静默吃掉真实代码参数**，
  那是数据损失，比体积问题严重。体积问题由 256KB 护栏兜底（R4）。

### R4（P0）两个阈值分立，别混成一个

- **`shedBulkDataUrls`**：只认 `data:` URL，且有最小长度下限 → 管"可剥的大块数据"。
- **256KB 护栏**：按**单节点序列化后的字节数**判，**不看是不是 data URL** → 管"剥不掉的超长字符串"
  （500KB 的 code 节点、超长文本参数）。命中即**拒写该快照**并提示，不污染历史。
- 两者**不合并**：一个"已剥离"的快照不等于"已受限"，13b 用例造的就是这个缝。

### R5（P0）上限 20 与淘汰

- 每工作流最多 **20 个版本**；超出淘汰**最旧**。
- 淘汰只删快照，**不动 revision 与其历史**。
- 列表顶部一行小字说明"仅保留最近 20 个版本"。

### R6（P0）存储结构

- **不进工作流 JSON**：轻索引 `workflow-versions:<workflowId>`（每条几十字节的元信息）
  - **每版本一个键** `workflow-versions:<workflowId>:<version>`。
  * 理由：一次保存只写"一条快照 + 小索引"，而不是整键重写；删旧只删一个键。
- 与 `KEY_WORKFLOWS` 用同一套串行化（`withKeyLock`），避免并发保存互相覆盖。
- **体积上限 4 MB / 工作流**（按实测：200 节点 × 20 = 3.3 MB，刚好在 4 MB 内）；超限先淘汰最旧并提示。
- **上限必须可注入参数**（`limit` / `budgetBytes`）：否则按现在这体积分布，淘汰分支**永远触发不了**，
  就是一条永远绿的断言。合成大图单测（AC-12）靠它。
- **定位**：安全网（控制写入耗时与体积），**不是性能旋钮**；正常图有几千倍余量，不写进文档主路径。
- 读不到/损坏：显示空状态并提示，**不许让编辑器打不开**。

### R7（P0）列表信息与预览

- 摘要只写**能从两版 diff 读出来的**：节点数 `7→8`、边数变化、增删节点名（最多 3 个），**不编动机**。
- 预览**只读**：能看节点与连线，不能编辑、不能拖、不能保存；顶部标明"正在预览版本 N"，
  提供「应用这个版本」与「返回当前」。

### R8（P0）应用、回滚留痕与撤销

- 「应用」= 画布变为该版本；`pushHistory()` 记录**一次**撤销点；画布标记为**未保存**，由用户决定何时落盘。
- **撤销一次**回到应用前。
- **应用动作本身留痕**：新增一条 `source: 'rollback'` 的记录，显示「回滚自 vN」。
  - **只存引用**（`{source:'rollback', fromVersion, fingerprint}`），不复制 nodes/edges——20 条里塞重复内容
    等于把历史做小。
  - **回滚记录不可应用**（它只是留痕）；**源版本被删后**该条仍在，标注「源版本已删除」。

### R8b（P0）拒绝与淘汰必须有可见反馈

- **保存成功但没生成版本**时，状态行必须说明原因：`这次没有生成版本：某个节点超过 256KB，无法保存快照`。
  现状是 `saveWorkflowVersionSnapshot` 返回 `{saved:false, refused:'node-payload'}`，而调用点把它丢了
  （`index.ts:1947` 只用 `console.warn`）——用户点了保存、版本列表没动，会以为功能坏了。
- **超预算淘汰**时提示：`为节省空间，已淘汰最旧的 N 个版本`（对应返回值 `evicted: number[]`，同样不许丢）。
- 两类提示都走状态行（不打断操作的轻提示），**en + zh-CN 双侧**。
- **契约**：保存响应必须携带版本结果（`versions: {saved, refused?, evicted}`）——否则前端只能猜。
  2026-11-24 实测：响应是空壳 `{type:'workflows.save'}`，编辑器里 `saved.versions` 永远不成立，
  **文案写了、分支写了、永远不触发**。同一批还漏了另外两处接线：`saveWorkflow` 的返回值被丢掉、
  快照仍吃调用方形态——三处必须一起接。

### R9（P0）删除

- 任意版本可删；删除**不改画布**；需要二次确认，文案说明"只删历史记录，不影响当前工作流"。
- **唯一例外：与当前画布内容一致的那条（"当前版本"）不可删**——它是"你现在在哪"，删了列表就无法定位当前状态。
  按钮置灰并提示。
- **"当前版本"的口径 = 指纹与当前画布比对**：一致才标「当前」并禁止删除；
  **匹配不到（改了画布没保存）则一条都不标"当前"，任何版本都可删**。
  不用"最新一条"判断——应用旧版后会出现"删不掉的那条"死角。
- **应用旧版后 = 那一版是"当前"**（2026-11-24 定 (a)）：画布内容确实等于它，标「当前」符合直觉。
  所以"应用未保存"**不算**"匹配不到"；只有"改了画布没保存"才是。

### R10（P0）持久化与隔离

- 按 `workflowId` 存；刷新 / 重开编辑器后仍在。
- **A 的版本不出现在 B 里**；工作流被删除时级联清理它的版本键（不留孤儿）。

### R11（P1）文案与样式

- 新增文案 en + zh-CN 双侧（`src/workflow-editor/i18n.ts`）；样式用 Tailwind + 语义 token（AGENTS §2/§3）。

## 6. 暂不采纳

| 想法                                         | 不做的原因                                                  | 未来触发条件                                            |
| -------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| 快照复用 `revisionHistory` / 存进工作流 JSON | 历史进 JSON → 每次保存内容都不同 → 判等永远失败、体积一路涨 | 不做                                                    |
| 用时间戳判等                                 | 同秒两次保存误判；"没改也保存"也会新增                      | 不做                                                    |
| 快照单独加 8KB 截断                          | 落盘不截断而快照截断 → 应用旧版静默吃掉真实参数，是数据损失 | 若 `saveWorkflow` 自己也截断，则同批跟进（R3 耦合约束） |
| 只记手动保存                                 | 用户要的是"工作流什么时候变过"，AI 改坏也要能回去           | 不做；来源标清楚                                        |
| 无限历史 / 分页                              | 与"最多 20"冲突，存储不可控                                 | 用户明确要求更多时                                      |
| 版本命名 / 完整 diff 视图                    | 本次不含；时间 + 摘要足够定位                               | 摘要不够用时                                            |
