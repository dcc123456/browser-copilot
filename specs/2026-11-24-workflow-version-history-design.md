# 工作流保存版本历史 / Workflow save-version history

> **文档状态**：需求与验收标准（产品侧）。实现方案由 `世界级开发程序员` 补（§7）。日期 2026-11-24。

## 2. 现状事实（代码级，决定了这不是"加个列表"）

- **保存链路**：编辑器保存按钮 → `App.tsx:911` 的 `handleSave` → `workflows.save`；worker
  （`background/index.ts:1902-1943`）在落盘前调用 `commitWorkflowRevision`，把 `revision` 加一、
  追加一条 `revisionHistory`。
- **每次保存都 +1，不看内容变没变**：`commitWorkflowRevision`（`lib/workflow/workflow-revision.ts:52`）
  的编号取自当前 workflow，**没有内容比较**。所以"连续保存两次、中间没改"现在会产生 **2 条** revision，
  与用户要的"没更新就不新生成版本"直接冲突。
- **已有上限 20，但只是元数据**：`REVISION_HISTORY_LIMIT = 20`（`workflow-revision.ts:20`）；
  `WorkflowRevisionMetadata` 只有 `revision / updatedAt / source / parentRevision / repairSessionId`
  （`lib/workflow/types.ts:285-291`）——**没有图快照**，所以"应用旧版本"目前**无法实现**。
- **历史存在工作流 JSON 内部**：`revisionHistory` 是 `Workflow` 的一个字段（`types.ts:357`）。
  这与"历史不能进工作流 JSON"的约束冲突：一旦历史在 JSON 里，**每次保存的内容都会因为"历史多一条"而不同**，
  按内容判等永远不相等。
- **来源词表已存在**：`source: 'manual-edit' | 'ai-repair' | 'generation' | 'marketplace' |
'marketplace-update'`（`types.ts:288`）——版本列表可以沿用这套来源标签，不必新造。
- **入口位置**：工具栏 tab 依次是 日志 / 目标 / 数据表 /（参数），`TopToolbar.tsx:136-143`；
  「版本」放在「数据表」之后。
- **撤销**：编辑器有 `pushHistory`（`App.tsx:390`）与 AI 改动的整批快照；"应用旧版本"必须能**一次撤销**。

## 3. 产品判断（先把两件事拆开）

- **编号（revision）** 已经存在，服务的是并发控制与来源留痕（AI 修复、广场更新都靠它判断"基线没被改"）。
  **本次不动它**——否则会牵动修复与市场两条链路。
- **快照（version）** 才是用户要的"能回去的版本"。它需要新存：图 + 元信息，**独立于工作流 JSON**。
- 所以本需求 = **在既有 revision 之上补一层快照**，并让"内容没变不新增版本"成立。两者可以并存：
  revision 继续每次保存 +1（内部语义），version 只在**内容变化**时新增。

## 4. 需求

### R1（P0）入口与弹窗

- 工具栏「数据表」按钮**右侧**新增「版本」按钮（图标 + 文案，中英双语）；点击打开弹窗。
- 弹窗内容：版本列表（倒序）、每行的时间 / 来源 / 摘要 / 大小，行内操作：**预览**、**应用**、**删除**。
- **空状态**：还没有任何版本时显示一句"保存一次后这里会出现版本"，不显示空表格。
- **关闭**：点遮罩、Esc、右上角关闭都只关弹窗，**不改变画布**。

### R2（P0）什么算"一个版本"

- **只有内容变化才新增版本**。判等用**规范化内容的哈希**，不是时间戳、不是 revision 号。
- **参与判等的内容**：节点（含类型、参数、id、位置）、边、触发器、工作流名称/描述/设置、参数声明。
- **不参与判等**：画布视口（`drawflow.position` / `zoom`）、`updatedAt`、`revision`、`revisionHistory`、
  **版本历史本身**。→ 只平移/缩放画布、或只是"历史多了一条"，都**不产生新版本**。
- **哪些动作算一次保存**：编辑器保存按钮、工作流生成落盘、AI 修复落盘、广场更新落盘——
  **都记版本**，但 `source` 按真实来源标注（沿用现有词表），列表里能看出"这版是 AI 改的"。
- **不算保存**：参数面板保存（`workflows.parameterValues`，它刻意不动图）、纯浏览、运行。

### R3（P0）上限 20 与淘汰

- 每个工作流最多保留 **20 个版本**；超出时淘汰**最旧**的。
- 淘汰只删快照，**不影响 `revision` 编号与 `revisionHistory`**（两套东西互不干扰）。
- 淘汰必须**静默发生但可解释**：列表顶部一行小字"仅保留最近 20 个版本"。

### R4（P0）列表信息

- 每行：**时间**（本地时区，`YYYY-MM-DD HH:mm`）、**来源**（手动 / 生成 / AI 修复 / 广场更新 / 回滚）、
  **摘要**（相对上一版：节点数 `7→8`、边数变化、新增/删除的节点名，最多列 3 个）、**大小**（KB）。
- 摘要**不许编动机**：只写能从两版 diff 里读出来的东西。

### R5（P0）预览

- 点「预览」进入**只读**视图：能看到该版本的节点与连线，**不能编辑、不能拖、不能保存**。
- 预览里必须明确显示"正在预览 v12（2026-11-24 10:31）"，并提供「应用这个版本」与「返回当前」。

### R6（P0）应用与回滚留痕

- 点「应用」→ 画布变为该版本的内容；**并且这次应用本身生成一条新版本**，`source: 'rollback'`，
  摘要写「回滚自 v12」。
  - 理由：不留痕的话，用户回滚完就**再也回不到回滚前**——这是"版本历史"最容易做错的一步。
- 应用**必须是一次可撤销的操作**：`撤销` 一次回到应用前的画布（复用 `pushHistory` 语义）。
- 应用后画布处于**未保存**状态（保存按钮显示脏标记），由用户决定何时落盘；不自动保存。

### R7（P0）删除

- 任意历史版本可手动删除；删除**不改变当前画布**。
- **禁止删除"当前画布对应的版本"**（即最新一条与画布内容一致的版本），按钮置灰并提示"这是当前版本"。
- 删除需要**二次确认**（不可撤销的操作），文案说明"只删除历史记录，不影响当前工作流"。

### R8（P0）持久化与隔离

- 版本按 **`workflowId`** 存**独立键**，**不进工作流 JSON**；刷新页面、重开编辑器后仍在。
- **A 的版本不会出现在 B 里**；工作流被删除时，它的版本一起清理（不留孤儿数据）。
- 存储读不到 / 值损坏时：列表显示空状态并提示，**不许让编辑器打不开**。

### R9（P0）体积上限

- 每个工作流的版本存储上限 **2MB**；超限时**先淘汰最旧**，并在弹窗里提示"为节省空间，已淘汰最早的版本"。
- **不许静默撑爆存储**，也不许因为版本超限让保存失败。

### R10（P1）文案与样式

- 所有新增文案 en + zh-CN 双侧（`src/workflow-editor/i18n.ts` 独立字典，AGENTS.md §3）；
- 样式只用 Tailwind + 语义 token（AGENTS.md §2）。

## 5. 验收标准

| 编号  | 对应需求 | 判据                                                                                            | 方法             |
| ----- | -------- | ----------------------------------------------------------------------------------------------- | ---------------- |
| AC-1  | R2       | 连续保存两次、中间没有任何修改 → **版本数不变**（且 `revision` 仍按既有语义递增，两者互不干扰） | 单测 + 真机      |
| AC-2  | R2       | **只平移/缩放画布**后保存 → **不产生新版本**                                                    | 真机             |
| AC-3  | R2       | 改一个节点参数后保存 → **+1 条**，摘要能看出节点数/边数或节点名变化                             | 真机             |
| AC-4  | R3       | 连续保存 21 次（每次都有内容变化）→ 列表 **20 条**，最旧的被淘汰，最新在最上                    | 单测 + 真机      |
| AC-5  | R6       | 应用旧版本 → 画布等于该版本；**列表新增一条「回滚自 vN」**；`撤销` 一次回到应用前               | 真机             |
| AC-6  | R7       | 删除中间版本 → 画布不变、列表少一条；删除**当前版本**被禁止并提示                               | 真机             |
| AC-7  | R8       | 刷新 / 重开编辑器后版本仍在；A、B 两个工作流的版本互不出现；删除工作流后其版本被清理            | 真机 + 存储断言  |
| AC-8  | R9       | 版本存储超过 2MB → 淘汰最旧并提示；**保存本身不失败**                                           | 单测（构造大图） |
| AC-9  | R1 / R10 | 入口在「数据表」右侧；弹窗可关且不改画布；空状态正常；全部文案中英双语                          | 真机 + 类型检查  |
| AC-10 | R2       | 参数面板保存（`workflows.parameterValues`）**不产生版本**                                       | 真机             |

**不触发的 AC 不算通过**：AC-1 / AC-2 必须真的"保存两次/只动视口"再去看列表，
不能只断言"哈希函数相等"。

## 6. 暂不采纳

| 想法                                            | 不做的原因                                                                        | 未来触发条件             |
| ----------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------ |
| 把快照存进工作流 JSON（复用 `revisionHistory`） | 历史进 JSON → 每次保存内容都不同 → 判等永远失败、体积一路涨；这正是本次要避开的坑 | 不做                     |
| 用时间戳判等                                    | 同一秒内两次保存会误判为不同；反过来"保存了但没改"也会新增                        | 不做                     |
| 只记手动保存，不记 AI 修复 / 生成 / 广场更新    | 用户要的是"工作流什么时候变过"，AI 改坏也需要能回去                               | 不做；但来源要标清楚     |
| 无限历史 + 分页                                 | 与"最多 20 个"直接冲突，且存储不可控                                              | 用户明确要求更多时再评估 |
| 版本命名 / 备注                                 | 本次不含；20 条用时间 + 摘要足够定位                                              | 用户提出"想给版本起名"时 |
| 版本对比视图（左右 diff）                       | 摘要已给增删节点；完整 diff 是独立功能                                            | 摘要不够用时             |

## 8. 待验证假设

1. **工作流 JSON 的体积分布**：2MB 上限是否合理——如果单图就有 1MB，20 个版本会立刻触发淘汰。
2. **快照里有没有大对象**：节点参数可能含 data URL / 长文本（脚本、提示词），直接整图存会放大存储。
3. **`revision` 的既有消费者**：AI 修复、广场更新依赖 `revision` 判断基线；新增快照层不能改变它们的行为。
4. **"当前版本"的判定口径**：用内容哈希与画布当前内容比对（推荐），还是用"最新一条"——两者在"应用旧版本后未保存"时会分叉。
